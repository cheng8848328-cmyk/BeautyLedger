# BeautyLedger v0.2.0 — 实验性 MVP（待发布）

本地命令行收支与员工提成记录工具。仅使用 Python 标准库，面向单进程串行操作；不依赖 MySQL、第三方 Python 包或独立练习文件 `sqlite_practice.py`。

0.2 是实验性 MVP，尚未经过真实门店工资结算验证。适合使用虚构数据评估功能，不应将程序输出直接视为已审批的工资或退款依据。建议发布标签为 `v0.2.0`；当前 CLI 标题仍显示 `BeautyLedger v0.2`。

## 环境与 Windows + VS Code 运行步骤

要求 Python 3.10 或更高版本。本轮实际验证版本为 Windows 上的 Python 3.12.15；其他版本尚未逐一验证。

1. 安装 Python，在 VS Code 中打开包含 `main.py` 的 `BeautyLedger_App` 文件夹。Python 扩展可选。
2. 打开 VS Code 的 PowerShell 终端，确认当前目录包含五个业务模块和 `tests/`。若打开的是外层目录，先执行 `cd .\Practice_41_47\BeautyLedger_App`。
3. 检查版本并启动：

```powershell
py -3 --version
py -3 -B main.py
```

若没有 `py`，可使用 `python --version` 和 `python -B main.py`。两者均不可用时，在 VS Code 选择已安装的 Python 解释器，并用其实际完整路径运行；不要原样照抄占位路径：

```powershell
& 'C:\实际安装目录\python.exe' --version
& 'C:\实际安装目录\python.exe' -B main.py
```

首次运行无需创建 `data/`。文件不存在时从空账本开始，首次成功保存才创建相应文件。请只运行一个实例，运行期间不要手工编辑、恢复或同步覆盖账本。

## 菜单 0–9

| 菜单 | 实际功能 |
| --- | --- |
| 0 | 退出；Ctrl+C 或输入结束也会退出 |
| 1 | 录入收入：正整数 SGD 与备注，成功保存后更新内存 |
| 2 | 录入支出：正整数 SGD 与备注 |
| 3 | 查看收支记录，不包含提成明细 |
| 4 | 汇总收入、支出和收支差额；不是银行或会员余额 |
| 5 | 单人服务提成：员工 ID、月份、原价、显式比例、完成状态 |
| 6 | 会员充值销售提成：员工 ID、月份、充值金额，固定 5% |
| 7 | 双人服务：两个不同员工 ID，共用总提成并各分一半，一次保存两条 |
| 8 | 按月份显示各员工净提成，包含该月冲回、零额和负净额 |
| 9 | 按原始 `entry_id` 全额冲回单条正向提成；预览后明确输入 `YES` 才保存 |

菜单 5–8 的输入提示支持 `q` 返回；菜单 9 的 ID、月份提示支持 `q`，最终确认除精确的 `YES` 外均取消。输入无效会返回菜单，本次未保存。菜单 1–2 保留 0.1 行为，不支持 `q` 作为统一取消命令，备注中的 `q` 是普通文字。

员工 ID 区分大小写，录入时去除首尾空白，不校验员工名册。月份为 `YYYY-MM`，合法范围 `0001-01` 至 `9999-12`，不自动推定当前月份。

## 金额与计算规则

- 金额存储、计算和汇总使用 SGD 整数分，显示固定两位小数，不用浮点金额。
- 菜单 1–2 仍只接受正整数 SGD。菜单 5–7 接受正整数或恰好两位小数，如 `60`、`60.00`、`60.50`；不接受 `60.5`、科学计数法或千位分隔符。
- 服务比例必须逐笔明确输入 `0` 至 `100` 的百分数，最多两位小数，不含 `%`。1 基点 = 0.01%，10000 基点 = 100%；例如 `12.5` 对应 1250 基点。
- 已完成服务：`原价分 × 比例基点 ÷ 10000`。依据原价，不依据折后实收。未完成服务保存零提成；之后没有自动转为完成的流程。
- 充值销售提成：`充值金额分 × 500 ÷ 10000`，固定 5%。不增加会员余额，也不自动记收入。
- 双人服务先计算一次总提成再平分。总提成为奇数分时拒绝保存；结果含不足一分时也拒绝计算，不截断、不四舍五入。
- 冲回金额严格等于原提成的负数，保留原明细，并用 `reversal_of_entry_id` 引用。每条正向明细最多冲回一次；零额、负额、冲回记录不能再冲回。
- 冲回月份由操作者明确输入，可跨月；原月保持原提成，指定月份计负数。没有自动重开历史月份或扣回已发工资。程序不限制冲回月份必须晚于原月，日期政策尚待业务确认。

## 数据文件与 Git 边界

路径相对于模块所在目录，不随启动终端的工作目录变化：

- `data/records.json`：旧收支账本。
- `data/commissions.json`：独立提成账本；不会修改旧收支或纳入菜单 4。
- `data/records-*.tmp`、`data/commissions-*.tmp`：保存时创建的临时文件，正常会清理，清理失败可能遗留。

新提成保留 `entry_id`、`transaction_id`、员工、月份、金额、类型、`audit_version=1` 及计算依据；双人明细共享交易 ID。旧的合法提成记录即使没有计算依据仍可读取，保存时不补字段或改写历史金额；旧格式无法提供完整计算审计证据。0.1 的整数分收支格式继续兼容，不支持任意其他旧格式自动迁移。

`.gitignore` 忽略整个根目录 `data/`，以及 Python 缓存、虚拟环境、`.env`/`.env.*`（`.env.example` 除外）与测试缓存。忽略规则不能移除已跟踪文件，也不是所有私钥或私人文件的通用过滤器。不要把备份放到未忽略的项目位置，不要使用强制添加数据文件的操作。

0.2 发布需包含：`main.py`、`ledger.py`、`storage.py`、`commission.py`、`commission_storage.py`、三个 `tests/test_*.py`、本 README 与 `.gitignore`。`sqlite_practice.py` 不属于发布范围；只复制这些发布文件，不复制正式数据、缓存、密钥或个人资料。

## 使用虚构数据验证

在仅包含上述发布文件的独立文件夹中演练，不在正式项目账本上尝试。依次启动 `main.py`，按提示输入，每组末尾选 `0` 退出，再启动下一组：

| 操作 | 依次输入 | 预期 |
| --- | --- | --- |
| 单人服务 | `5 → DEMO-ALICE → 2026-10 → 60 → 30 → y → 0` | 18.00 SGD |
| 充值提成 | `6 → DEMO-ALICE → 2026-10 → 1000 → 0` | 50.00 SGD |
| 双人服务 | `7 → DEMO-ALICE → DEMO-BOB → 2026-10 → 100 → 30 → y → 0` | 每人 15.00 SGD |
| 月度查询 | `8 → 2026-10 → 0` | ALICE 83.00、BOB 15.00 SGD |

菜单 8 不列出明细 ID。退出程序后，可用 VS Code **只读查看**演练副本的 `data/commissions.json`，找到单人服务 1800 分记录的 `entry_id`，复制该值，不编辑 JSON。再次启动，选择 `9`，粘贴 ID，输入 `2026-11`，核对预览后输入 `YES`，最后 `0`。重启查询：10 月 ALICE 仍为 83.00 SGD，11 月 ALICE 为 -18.00 SGD。对同一 ID 再次冲回应拒绝保存。

双人服务冲回只处理所选员工的一条明细，程序提示另一条关联明细，不自动冲回整笔交易。旧菜单可另用 `1 → 100 → 模拟收入 → 2 → 25 → 模拟支出 → 3 → 4 → 0` 验证，收支差额为 75.00 SGD，提成账本不变。

## 保存、备份与恢复

两类保存都先写同目录临时文件，关闭后通过 `os.replace` 替换正式文件。提成保存还执行 `flush/fsync`。常规读写或替换失败不会显示保存成功；双人记录作为一次完整快照写入。输入期间取消、EOF 或 Ctrl+C 不提交未完成录入；保存替换之后发生中断则数据可能已提交，重新录入前必须核查。

两个保存接口均在写入临时文件前重新加载并校验磁盘现有账本，要求全部历史明细作为待保存列表的完整前缀原样保留，且顺序不变。允许保存相同内容或在末尾追加合法新记录；拒绝删除、修改、替换、重排历史，也拒绝用空列表覆盖非空账本或用遗漏新增历史的旧快照覆盖当前文件。比较包括额外字段，并区分 `true`、`1` 和 `1.0`；JSON 对象键顺序不影响比较。

旧账本在启动时损坏会阻止整个程序启动；提成账本损坏会阻止对应提成操作，菜单 0–4 仍可用。**两类保存都会拒绝覆盖无法解析、格式校验失败或无法读取的现有文件。** 旧收支账本即使在程序启动后损坏，下一次保存也会失败，保留损坏文件原始字节，不自动清空、修复或迁移。

这是单进程串行保存接口的保护，不是并发锁或不可篡改审计。检查与替换之间仍有竞争窗口；直接编辑、替换或删除磁盘文件可绕过保护。文件缺失仍按首次运行处理，无法区分首次创建与外部删除。不要同时运行多个实例或让同步工具覆盖数据。

当前不提供历史记录编辑功能。发现错误不能把直接修改 JSON 作为正常业务操作；符合条件的正向提成可通过菜单 9 追加全额冲回，其他更正应停止相关录入、保留原始证据并另行确认处理方案。读取 ID 时仅查看文件，不修改内容。

备份步骤：退出所有实例，将整个 `data/` 复制到项目之外的受保护、带日期目录；两个 JSON 一起保留，勿公开上传。没有对应业务记录时某个文件可能尚未生成。程序不自动备份、不加密文件，也不保证断电后的持久性。

恢复步骤：先退出程序，另存当前完整 `data/`（包括损坏文件）以便调查；在独立副本中验证备份能读取，再恢复同一备份时点的完整文件。不要把冲回记录与原明细分拆恢复，不要用空列表覆盖损坏文件。恢复旧备份会丢失备份之后的记录，需要人工核对。临时文件不等于可用备份。

## 已确认规则、待确认事项及限制

本版实现的规则：服务按原价和显式比例计算；未完成为零；充值固定 5%；双人等分；整数分精确计算；单条全额冲回且显式选月。这些是当前实现约定，不代表所有实际经营政策均已获确认。

尚待业务确认：不足一分的舍入、奇数分分配、默认服务比例、不同员工比例与双人非等额分配、阶梯提成、奖金、部分退款、退款授权、跨月工资调整与工资扣回政策、可冲回月份范围，以及未完成服务后续转完成流程。当前双人服务只有共同总提成等分，不支持逐员工差异比例、阶梯提成或奖金计算。技术上支持显式选月的提成冲回，不代表已经支持跨月工资调整。

当前限制与已知风险：

- **不能防止重复真实交易（P1）**：每次录入生成新的随机交易 ID；同一服务或充值重复输入会再次计提。没有外部订单号或幂等键，必须人工核对。
- **并发和磁盘直接改写仍有风险**：只追加保护仅约束保存接口；检查之后的并发写入仍可能被覆盖，也无法检测已被外部替换成合法格式的历史。仅支持一个实例串行使用。
- 旧收支存储虽已增加重读校验与历史保护，但仍没有提成存储的重复 JSON 字段拒绝和 fsync 加固；不应把所有形式的文件异常都视为可检测。
- 没有提成明细列表菜单、导出、员工管理、编辑撤销、部分冲回或整笔双人交易自动冲回。新录入成功提示也不显示明细 ID，冲回前需只读查看 JSON。
- 没有真正退款支付、会员余额管理、薪资发放、审批控制、用户权限或多用户并发。`YES` 只是本地操作确认，不是业务审批。
- 没有自动对账、自动备份、文件防篡改、异常退出恢复保证或大数据量性能保证。全量校验与 JSON 快照适合小规模本地使用。
